# ADR: Dynamic Flow Definition Format

**Status**: Accepted  
**Date**: 2026-03-30  
**Authors**: Research Duty (Copilot)  
**Related Research**: `/research/dynamic-flows/`

---

## Context

DataFlow pipelines are currently defined entirely in C# at compile time:
```csharp
services.AddDataFlows("global", df =>
{
    df.AddBlock("producer", ...);
    df.AddActorBlock<int, string, TransformActor>("transform");
    df.AddGraph("pipeline", g =>
    {
        g.UseBlock("producer").UseBlock("transform").Connect("producer", "transform");
    });
});
```

This is appropriate for well-understood, stable pipelines but prevents:
1. **Designer features**: no way to let non-developers compose pipelines visually
2. **Runtime reconfiguration**: changing a pipeline requires a code change and redeploy
3. **Pipeline-as-data**: cannot store, version, or audit pipeline topologies in a database

The `IBlockTypeRegistry` already stores `InputType`/`OutputType` for every registered block,
providing the metadata needed to validate dynamic compositions at runtime.

---

## Options Considered

### Option 1: JSON Definition with Flat Block List

```json
{
  "flowId": "my-flow",
  "version": 1,
  "blocks": [
    { "instanceId": "step1", "blockKey": "global:producer" },
    { "instanceId": "step2", "blockKey": "global:transform" }
  ],
  "connections": [
    { "from": "step1", "to": "step2", "bufferCapacity": 100 }
  ]
}
```

**Pros**:
- Zero new dependencies (`System.Text.Json` built-in)
- Trivially serializable by a designer canvas
- Natural fit for REST API transport
- Machine-friendly (no YAML whitespace sensitivity)

**Cons**:
- Less human-readable than YAML for large definitions
- `instanceId` and `blockKey` are currently coupled (no aliasing in v1)

### Option 2: YAML Definition

Same structure but in YAML.

**Pros**:
- More human-readable for hand-authored definitions

**Cons**:
- Requires `YamlDotNet` or similar dependency
- Conversion step needed before API transport
- Whitespace-sensitive (fragile in editors)

### Option 3: Code-Generated C# (DSL)

Generate a class implementing `IDataFlowDefinition` from a text description.

**Pros**:
- Strongly-typed at compile time

**Cons**:
- No runtime composition — defeats the purpose
- Complex and fragile

---

## Decision

Use **JSON** (Option 1) for the flow definition format, implementing:

1. A `FlowDefinition` C# model with `System.Text.Json` serialization
2. A `DynamicFlowBuilder` that validates and builds a `DataFlowGraph` from the definition
3. An `IFlowDefinitionRepository` abstraction with EF Core default implementation
4. A `DynamicFlowRunner` service following the existing runner pattern
5. New HTTP endpoints on `DataFlow.Blazor.Server` for definition CRUD and execution

**Why JSON over YAML**: Zero dependencies, native API transport, machine-generated by the
designer canvas, sufficient human-readability for a machine-managed format.

**YAML** can be offered as an optional read layer in a future version for users who prefer
to hand-author definitions.

---

## Consequences

### Positive

- No new runtime dependencies
- Builds on existing `IBlockTypeRegistry` and `DataFlowGraphBuilder` — no new execution paths
- Definitions are auditable database records (version-controlled)
- Blocked type mismatch errors surface before execution, with clear messages
- Existing visualization (FlowRunsList, FlowVisualization) works without changes
- Opens the path to a visual designer UI

### Negative

- `instanceId` and `blockKey` are coupled in v1 (no aliasing). Using the same block type
  twice in one flow requires a dedicated registration for each instance.
- Block configuration is not bound in v1 — blocks use hardcoded defaults until Phase 2.

### Neutral

- Flow definitions are stored in a new database table alongside visualization data
- The `IFlowDefinitionRepository` abstraction lets applications use alternative storage
  (filesystem, blob) without changing the core library
