# Profiling Benchmarks Implementation Summary

## Overview

This implementation provides a comprehensive benchmarking solution for tracking DataFlow pipeline performance using a sophisticated ETL workload. It addresses the need to move beyond simple aggregate metrics and enables performance tracking with external tooling.

## Problem Statement

While BenchmarkDotNet provides excellent aggregate metrics, the original issue identified needs for:
1. Real-world ETL scenario benchmarking with multiple block types
2. Integration with standard .NET profiling tools (dotnet-trace, dotnet-counters)
3. OpenTelemetry metrics export for trend analysis
4. Routing, batching, broadcasting, and transformation patterns

## Solution Architecture

### 1. Reusable Complex ETL DataFlow (`Benchmarks/Shared/ComplexEtlDataFlow.cs`)

A sophisticated benchmark pipeline using **StructuredDataFlowBuilder** that models real-world data processing.

**Pipeline Structure:**

See the auto-generated Mermaid diagram at: [docs/diagrams/complex-etl-benchmark.md](../../docs/diagrams/complex-etl-benchmark.md)

The diagram is regenerated by running:
```bash
dotnet test --filter "Category=Documentation"
```

**Block Types Exercised:**
- Producer blocks for data generation
- Transform blocks for validation, enrichment, processing, aggregation
- **Broadcast blocks** for fan-out to parallel processors (metrics collection, audit logging)
- **Routing blocks** for category-based routing to different processing paths
- Batch blocks for grouping and time-windowing
- Processor blocks for sink operations (simulated I/O)
- Multiple concurrent workers (configurable MaxConcurrency)

**Configurable Parameters:**
- `RecordCount`: Number of records to process (default: 10,000)
- `MaxConcurrency`: Degree of parallelism (default: 4)
- `BatchSize`: Records per batch (default: 100)

### 2. Dual Execution Modes

**BenchmarkDotNet Mode (`etl-benchmark`):**
- Statistical rigor with warmup, iterations, outlier detection
- Comparative performance analysis across code changes
- Full reporting with percentiles and standard deviation
- Optional OpenTelemetry export via environment variables

**Direct Execution Mode (`etl-direct`):**
- Bypasses BenchmarkDotNet to enable external profiling tools
- Runs dataflow directly in main process (not child processes)
- Works with dotnet-trace, dotnet-counters, OpenTelemetry
- Configurable: `etl-direct [recordCount] [iterations]`

### 3. External Profiling Tools Integration

**dotnet-trace** - CPU sampling and flame graphs:
- Automated via `profile-with-trace.sh` (Linux/macOS) and `profile-with-trace.ps1` (Windows)
- Generates `.nettrace` files viewable in PerfView, SpeedScope, Visual Studio
- Converts to speedscope format for web-based flame graph visualization

**dotnet-counters** - Live performance monitoring:
- Monitor System.Runtime, Uniun.DataFlow meters in real-time
- CSV export for time-series analysis
- Low overhead continuous monitoring

**OpenTelemetry** - Metrics export:
- Export DataFlow metrics to OTEL collectors
- Configure via environment variables
- Integration with Grafana/Prometheus for dashboards
- Resource attributes for commit SHA, version tagging

### 4. Documentation Test (`ComplexEtlDiagramTests.cs`)

XUnit test with `[Category("Documentation")]` that:
- Builds the complex ETL dataflow using shared definition
- Generates Mermaid diagram from StructuredDataFlowBuilder graph
- Outputs to `docs/diagrams/complex-etl-benchmark.md`
- Ensures documentation stays synchronized with implementation

## Usage Examples

### Quick Start - BenchmarkDotNet
```bash
cd src/Benchmarks
dotnet run -c Release -- etl-benchmark
```

### Quick Start - Direct Execution for Profiling
```bash
# Simple execution
dotnet run -c Release -- etl-direct 100000 3

# With dotnet-trace
dotnet-trace collect --process-id <PID> & dotnet run -c Release -- etl-direct 100000 1

# With OpenTelemetry
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317 dotnet run -c Release -- etl-direct 50000 1
```

### Automated Profiling with dotnet-trace
```bash
cd src/Benchmarks
./Profiling/profile-with-trace.sh 100000 1      # Linux/macOS
.\Profiling\profile-with-trace.ps1 100000 1    # Windows
# Upload generated .speedscope.json to https://www.speedscope.app
```

### Before/After Comparison Workflow
1. Baseline: `dotnet run -c Release -- etl-direct 50000 5`
2. Make library improvements
3. After: `dotnet run -c Release -- etl-direct 50000 5`
4. Compare BenchmarkDotNet reports or OTEL metrics in Grafana
5. Analyze flame graphs for hotspots

## Design Decisions

### Why Complex ETL?
- Exercises multiple block types in realistic scenarios
- Demonstrates backpressure handling with concurrent paths
- Models common patterns (validation, enrichment, routing, batching, broadcasting)
- Scalable with configurable parameters for different workloads

### Why External Tooling Over In-Process Sampling?
- **Lower overhead**: No instrumentation code affecting measurements
- **Standard tooling**: dotnet-trace, dotnet-counters are battle-tested
- **Better separation**: Benchmark focuses on dataflow, tools focus on metrics
- **OpenTelemetry integration**: Industry-standard metrics collection

### Why Two Execution Modes?
- **etl-benchmark**: BenchmarkDotNet for statistical comparative analysis
- **etl-direct**: Direct execution for external profiling tools (dotnet-trace, dotnet-counters)

This addresses the limitation where BenchmarkDotNet runs benchmarks in child processes, preventing external tools from capturing metrics when attached to the parent process.

### Why Simulated I/O Instead of In-Memory Storage?
- **Realistic**: Models database/file writes with async delays
- **Lower memory pressure**: No accumulation of processed data
- **Scalable**: Can run high-volume benchmarks without memory constraints
- **Focused**: Benchmark measures dataflow performance, not memory allocation

## Integration with CI/CD

The benchmarks can be integrated into CI/CD pipelines:

```yaml
- name: Run Performance Benchmarks
  run: |
    cd src/Benchmarks
    dotnet run -c Release -- etl-benchmark
    
- name: Upload Results
  uses: actions/upload-artifact@v3
  with:
    name: benchmark-results-${{ github.sha }}
    path: src/Benchmarks/BenchmarkDotNet.Artifacts/
```

For OpenTelemetry-based tracking:
```yaml
- name: Run with OTEL Export
  run: |
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4317
    export OTEL_RESOURCE_ATTRIBUTES="version=$VERSION,commit=$GITHUB_SHA"
    cd src/Benchmarks
    dotnet run -c Release -- etl-direct 100000 3
```

## Output Files

### BenchmarkDotNet Reports
- HTML and Markdown reports in `BenchmarkDotNet.Artifacts/results/`
- Statistical analysis with mean, median, p95, standard deviation
- Comparison across different parameters/commits

### dotnet-trace Outputs
- `.nettrace` files with CPU sampling data
- `.speedscope.json` files for flame graph visualization
- View in PerfView, SpeedScope, or Visual Studio

### dotnet-counters Outputs
- Real-time console output
- CSV exports for time-series analysis
- Metrics: CPU, memory, GC, thread count, DataFlow-specific counters

### OpenTelemetry Exports
- Metrics exported to configured OTEL collector
- Available in Grafana, Prometheus, Azure Monitor, etc.
- Queryable with PromQL, KQL, or other query languages
