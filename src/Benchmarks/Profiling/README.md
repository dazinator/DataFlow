# Profiling Benchmarks

This directory contains sophisticated profiling benchmarks designed to measure and track the performance of DataFlow pipelines over time. These benchmarks go beyond traditional BenchmarkDotNet aggregate metrics by providing time-series data and detailed profiling support.

## Overview

The profiling benchmarks include:

1. **Complex ETL Benchmark** - A sophisticated real-world ETL pipeline that exercises multiple block types
2. **Performance Sampler** - In-process time-series metrics collection (CPU, memory, GC)
3. **Integration with dotnet profiling tools** - Support for dotnet-trace, dotnet-counters, etc.

## Complex ETL Benchmark

The ETL benchmark models a realistic data processing pipeline with:

- **Data Ingestion**: Simulated data source producing records
- **Validation**: Input validation and sanitization
- **Enrichment**: External data lookup simulation with async delays
- **Broadcasting**: Fan-out to multiple parallel processors (metrics collection, audit logging)
- **Routing**: Category-based routing to different processing paths
- **Batching**: Aggregation of records into batches
- **Transformation**: Multiple transformation stages
- **Target Sinks**: Concurrent writers to different destinations

## Running Benchmarks

### 1. BenchmarkDotNet (Standard)

Run the benchmark with BenchmarkDotNet for aggregate statistics:

```bash
cd src/Benchmarks
dotnet run -c Release -- etl-benchmark
```

**Note:** BenchmarkDotNet performs extensive warmup iterations and statistical analysis, which means benchmarks take a considerable time to run (5-15 minutes depending on configuration). This is intentional to ensure statistically significant results. For quick profiling, use the `etl-direct` command instead.

This will:
- Execute multiple warmup and measured iterations for statistical significance
- Generate standard BenchmarkDotNet reports with mean, median, standard deviation
- Output results to `BenchmarkDotNet.Artifacts/`

### 2. Direct Execution (Recommended for External Profiling)

Run the benchmark directly without BenchmarkDotNet to enable external profiling tools (dotnet-trace, dotnet-counters, OpenTelemetry):

```bash
# Specify record count and iterations (no defaults)
dotnet run -c Release -- etl-direct 50000 1

# Higher volume for more detailed profiling
dotnet run -c Release -- etl-direct 100000 5
```

Arguments (both required):
- First argument: Number of records (default: 10000)
- Second argument: Number of iterations (default: 1)

This mode:
- Runs the dataflow directly in the main process (no child processes)
- Enables external profiling with dotnet-trace, dotnet-counters
- Supports OpenTelemetry metrics export via environment variables
- Ideal for flame graph generation and live performance monitoring

### 3. Using dotnet-trace for Flame Graphs (Automated)

Use the provided scripts for easy flame graph generation:

**Linux/macOS:**
```bash
# From Benchmarks directory
cd src/Benchmarks
./Profiling/profile-with-trace.sh [recordCount] [iterations]

# Example: Profile with 50,000 records
./Profiling/profile-with-trace.sh 50000 1
```

**Windows (PowerShell):**
```powershell
# From Benchmarks directory
cd src\Benchmarks
.\Profiling\profile-with-trace.ps1 [recordCount] [iterations]

# Example: Profile with 50,000 records
.\Profiling\profile-with-trace.ps1 50000 1
```

These scripts will:
- Automatically detect and navigate to the correct directory
- Install `dotnet-trace` if not present
- Build the benchmarks in Release mode
- Start the profiling run in the background
- Collect CPU profiling data with dotnet-trace
- Generate a .speedscope.json file for visualization
- Save results to `BenchmarkDotNet.Artifacts/profiling/`

Upload the generated .speedscope.json file to https://www.speedscope.app for interactive flame graphs.

**Troubleshooting:**
- If the script fails to find the process, the benchmark may complete too quickly. Try a larger record count (e.g., 100000+)
- On Windows, ensure you're running PowerShell (not Command Prompt) for the .ps1 script
- On Linux/macOS, ensure the script has execute permissions: `chmod +x Profiling/profile-with-trace.sh`

### 4. Using dotnet-trace Manually

For detailed CPU profiling with flame graphs:

```bash
# Install dotnet-trace if not already installed
dotnet tool install -g dotnet-trace

# Start the direct execution in the background
dotnet run -c Release -- etl-direct 100000 1 &

# Get the process ID (Linux/macOS)
PID=$(pgrep -f "Benchmarks")

# Windows PowerShell alternative:
# $PID = (Get-Process | Where-Object {$_.ProcessName -like "*Benchmarks*"}).Id

# Collect trace
dotnet-trace collect --process-id $PID --profile cpu-sampling --output trace_etl.nettrace

# After the run completes, convert to speedscope format
dotnet-trace convert trace_etl.nettrace --format speedscope

# Upload the .speedscope.json file to https://www.speedscope.app
```

### 5. Using dotnet-counters for Live Monitoring

Monitor runtime metrics in real-time:

```bash
# Install dotnet-counters if not already installed
dotnet tool install -g dotnet-counters

# Start the direct execution
dotnet run -c Release -- etl-direct 100000 1 &

# Get the process ID (Linux/macOS)
PID=$(pgrep -f "Benchmarks")

# Windows PowerShell alternative:
# $PID = (Get-Process | Where-Object {$_.ProcessName -like "*Benchmarks*"}).Id

# Monitor counters
dotnet-counters monitor --process-id $PID System.Runtime Uniun.DataFlow
```

To save counters to CSV for time-series analysis:

```bash
dotnet-counters collect --process-id $PID --output counters.csv --format csv
```

## Output Files

### BenchmarkDotNet Reports

Location: `BenchmarkDotNet.Artifacts/results/`

BenchmarkDotNet generates comprehensive HTML and Markdown reports with:
- Statistical analysis (mean, median, standard deviation, percentiles)
- Comparative performance across configurations
- Memory allocation statistics
- GC collection counts

### External Profiling Data

When using external tools, output varies by tool:

**dotnet-trace:**
- `.nettrace` files (CPU sampling, allocations)
- `.speedscope.json` files for flame graph visualization

**dotnet-counters:**
- `.csv` files with runtime metrics sampled over time
- Includes GC, thread pool, exception counts

**OpenTelemetry:**
- Metrics exported to configured OTEL collector endpoint
- View in Grafana, Prometheus, or your monitoring platform

### Console Output

The `etl-direct` command provides console output with:
- Iteration progress and timing
- Records processed per second
- Total execution time
- Completion status

Example output:
```
Iteration 1/3
Complex ETL Benchmark completed in 1,234 ms
Processed 50,000 records (40,517 records/sec)

Iteration 2/3
Complex ETL Benchmark completed in 1,198 ms
Processed 50,000 records (41,736 records/sec)
...
```

DataFlow library also emits structured logs showing block execution progress.

### Metrics via OpenTelemetry

When OpenTelemetry is configured, the DataFlow library exports metrics including:
- **`dataflow.flow.duration.ms`**: Flow execution time histogram
- **`dataflow.block.duration.ms`**: Block execution time histogram  
- **`dataflow.active.flows`**: Number of actively executing flows (gauge)
- **`dataflow.active.blocks`**: Number of actively executing blocks (gauge)
- **`dataflow.operations.completed`**: Total block operations completed (counter)
- **`dataflow.items.processed`**: Total business items processed (counter)

View these metrics in your monitoring platform (Grafana, Prometheus, Azure Monitor, etc.).

### Visualizing Time-Series Data

#### Using Python Visualization Script

The repository includes a Python script for easy visualization of profiling data:

```bash
cd src/Benchmarks/Profiling

# Plot a single profile
python visualize_profile.py ../../BenchmarkDotNet.Artifacts/profiling/complex_etl_iter1_*.csv

# Compare multiple profiles
python visualize_profile.py compare '../../BenchmarkDotNet.Artifacts/profiling/*.csv'

# Print summary statistics
python visualize_profile.py summary ../../BenchmarkDotNet.Artifacts/profiling/complex_etl_iter1_*.csv
```

Requirements: `pip install pandas matplotlib`

This will generate PNG files with:
- CPU utilization over time
- Memory usage over time
- GC collections and thread count over time
- Comparison charts when multiple profiles are provided

#### Manual Analysis with Python/pandas

You can use tools like Python/pandas, Excel, or any visualization tool to analyze the CSV files:

```python
import pandas as pd
import matplotlib.pyplot as plt

# Load data
df = pd.read_csv('complex_etl_iter1_20241012_123456.csv')

# Plot CPU and Memory over time
fig, (ax1, ax2) = plt.subplots(2, 1, figsize=(12, 8))

ax1.plot(df['TimeMs'], df['CPU%'])
ax1.set_ylabel('CPU %')
ax1.set_title('CPU Utilization Over Time')

ax2.plot(df['TimeMs'], df['MemoryMB'], label='Private Memory')
ax2.plot(df['TimeMs'], df['WorkingSetMB'], label='Working Set')
ax2.set_xlabel('Time (ms)')
ax2.set_ylabel('Memory (MB)')
ax2.legend()
ax2.set_title('Memory Usage Over Time')

plt.tight_layout()
plt.savefig('performance_profile.png')
```

4. Compare the JSON summaries and CSV files to see improvements in:
   - Throughput (records/sec)
   - Average duration
   - Memory consumption
   - GC pressure
   - CPU utilization patterns

## Customizing Benchmarks

### Adjusting Workload Parameters

Edit `ComplexEtlBenchmark.cs` to modify:

```csharp
[Params(10000, 50000, 100000)] // Number of records
public int RecordCount { get; set; }

[Params(1, 4, 8)] // Concurrency levels
public int MaxConcurrency { get; set; }

[Params(50, 100, 200)] // Batch sizes
public int BatchSize { get; set; }
```

### Modifying Pipeline Complexity

The ETL pipeline can be adjusted in the benchmark classes:
- Add more transformation stages
- Increase simulated work (delays)
- Add broadcast blocks for fan-out scenarios
- Implement routing logic for conditional processing
- Add error handling paths

### Adjusting Sampling Rate

In `PerformanceSampler.cs`, change the interval:

```csharp
public PerformanceSampler(string outputPath, int intervalMs = 100) // Default 100ms
```

Or when creating the sampler:

```csharp
using var sampler = new PerformanceSampler(outputPath, intervalMs: 50); // 50ms samples
```

## Performance Considerations

### Sampling Overhead

- Performance sampling has minimal overhead (~0.5-1% CPU)
- Default 100ms interval balances detail vs. overhead
- For very short benchmarks (<5s), consider 50ms intervals
- For long-running benchmarks (>1min), consider 500ms intervals

### BenchmarkDotNet vs Standalone

- **BenchmarkDotNet**: Better for comparing implementations, automatic warmup, statistical analysis
- **Standalone**: Better for profiling tools integration, detailed time-series, lower overhead

## Troubleshooting

### High Memory Usage

If you see excessive memory usage:
- Reduce `RecordCount` parameter
- Reduce pipeline `Capacity` settings
- Check for memory leaks in transformers

### Low Throughput

If throughput is lower than expected:
- Increase `MaxConcurrency` parameter
- Reduce artificial delays in transformers
- Check for bottlenecks in the pipeline (single-threaded blocks)
- Review CPU utilization patterns in CSV

### Inconsistent Results

If results vary significantly between runs:
- Ensure machine is not under load from other processes
- Increase number of iterations
- Use BenchmarkDotNet mode for automatic statistical analysis
- Check GC settings (Server GC vs Workstation GC)
